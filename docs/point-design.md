# 포인트 설계

고객이 가게에 충전해 둔 잔액(포인트)을 서버에 어떻게 저장하고 앱에 내려주는지 정리한 문서예요.
정해진 것과 아직 정할 것을 나눠 적었어요. 정책 값이 정해지면 이 문서부터 고쳐요.

## 1. 지금 범위

| 항목 | 상태 |
|---|---|
| 가게·포인트 묶음 테이블, `/api/wallet`이 실제 데이터를 돌려줌 | **구현됨** |
| 관리자 웹: 가게 추가·수정, 포인트 묶음 조회 | **구현됨** |
| 가게 주소·전화와 충전 상품, `/api/stores`(가게 목록·상세) | **구현됨**. 앱 가게 탭(03-01 가게찾기, 04-01 가게 상세)은 만드는 중이에요. 검색·관심 지역·필터·거리·찜·사진·메뉴·리뷰는 아직이에요 |
| 테스트 데이터 (`php artisan db:seed`) | **구현됨** |
| 충전·쓰기·환불 | 설계만. 이때 포인트 변동 기록 테이블을 함께 만들어요. 앱 탈퇴 화면(09-14)의 '환불 신청' 버튼도 이때 달아요 |
| 공유포인트 | 설계만. 넘겨주기인지 빌려주기인지부터 정해요 |
| 프랜차이즈 지점 | 05-07 지점 선택 화면을 만들 때 |

## 2. 용어

- **포인트**: 가게에 충전해 둔 잔액이에요. 단위는 `P`, 실제로 내는 돈은 `원`이에요.
- **충전포인트**(charge): 내가 할인된 금액으로 충전한 포인트예요.
- **공유포인트**(shared): 다른 회원이나 그룹에게서 받은 포인트예요. 아직 만들지 않았어요.
- **서비스포인트**(service): 가게가 감사의 뜻으로 준 포인트예요. 기한이 있어요.
- 처음에는 '캐시'라고 불렀는데 개발 용어 cache와 헷갈려서 바꿨어요. 리뷰·이벤트 적립금은 두지 않아요.

## 3. 데이터 구조

```
stores (가게 = 포인트를 쓰는 단위)        point_lots (포인트 묶음 = 충전 1건 또는 서비스포인트 지급 1건)
- id                                    - user_id   → users.id  (기록이 있으면 회원을 지울 수 없음)
- name                                  - store_id  → stores.id (기록이 있으면 가게를 지울 수 없음)
- kind  cafe·food·bakery·beauty·shop    - type      charge, service
- address  주소 (비워 둘 수 있음)          - amount    처음 받은 포인트
- phone    전화번호 (비워 둘 수 있음)      - balance   남은 포인트
                                        - paid_won  충전할 때 낸 돈(원). 서비스포인트는 비움
charge_products (충전 상품)              - expires_on 이 날까지 쓸 수 있음
- store_id  → stores.id (가게를 지우면 함께 지움)
- amount    충전되는 포인트
- price_won 내는 돈(원). amount보다 클 수 없음
```

- **포인트는 가게마다 따로예요.** 충전한 포인트는 그 가게에서만 써요(시안 04-07).
- **프랜차이즈는 브랜드 하나가 가게 하나예요.** 충전한 포인트를 같은 브랜드의 모든 지점에서 써요(시안 05-07). 지점 목록은 지점 선택 화면을 만들 때 따로 둬요.
- **묶음마다 유효기간이 따로 있어요.** 같은 가게에 두 번 충전하면 묶음이 두 개이고, 지갑에도 두 줄로 보여요.
- **다 쓰거나 기한이 지난 묶음도 지우지 않아요.** 아낀 금액, 이전 가게(05-08), 환불 계산에 써요.
- **충전 상품은 가게가 정해요.** 예: 50,000P를 47,500원에. 할인율은 `(amount − price_won) ÷ amount`이고, 소수점은 버려서 실제보다 크게 보이지 않게 해요.
- 업종(`kind`)은 앱의 아이콘 묶음과 같은 다섯 가지예요. 시안 03-03의 세부 업종(한식, 분식 등)은 가게 찾기를 만들 때 따로 둬요.

## 4. 앱 API

### `/api/wallet` (내 가게 탭 05-01)

응답 모양은 앱 `PointRepository`가 읽는 그대로예요.

- **쓸 수 있는 묶음**만 보여줘요: 남은 포인트가 있고 `expires_on`이 오늘이거나 그 뒤인 묶음이에요. 마지막 날은 `days_left: 0`이에요.
- **가게 순서**: 쓸 수 있는 묶음 중 가장 최근에 받은 묶음이 있는 가게가 위예요.
- **묶음 순서**: 충전 → 공유 → 서비스, 같은 종류는 기한이 빠른 것부터예요.
- **아낀 금액**(`saved_won`): 충전 묶음마다 `amount − paid_won`을 더해요. 다 썼거나 기한이 지난 묶음도 넣어요.
- **공유포인트**(`shared`)는 0, **방문 횟수**(`visit_count`)는 쓰기 기록이 없어서 0이에요. 앱은 0이면 방문 횟수를 숨겨요.
- 날짜는 서버 시간대 `Asia/Seoul` 기준이에요.

### `/api/stores` (가게찾기 03-01, 가게 상세 04-01)

- **목록**(`GET /api/stores`): 모든 가게를 등록한 순서로 줘요. 가게마다 충전 상품 중 가장 큰 할인율(`max_discount_rate`)을 함께 주고, 충전 상품이 없으면 `null`이에요. 지역·거리 정렬을 만들 때 페이지로 나눠요.
- **상세**(`GET /api/stores/{id}`): 주소·전화와 충전 상품(`charge_products`)을 포인트가 작은 순으로 줘요. 상품마다 할인율(`discount_rate`)이 있어요.
- 둘 다 로그인해야 볼 수 있어요. 고객 앱이 로그인한 뒤에만 열리기 때문이에요.

## 5. 관리자 웹

- **가게**: 추가·수정만 해요. 포인트 기록이 있는 가게는 DB가 지우지 못하게 막아서 삭제 버튼은 두지 않아요. 주소·전화와 충전 상품도 가게 추가·수정 창에서 넣어요.
- **포인트**: 조회만 해요. 회원·가게로 찾고, 종류로 거를 수 있어요. 포인트는 충전·지급 기능으로만 생기고 관리자 웹에서는 만들거나 고치지 않아요.
- **회원**: 삭제 버튼을 뺐어요([auth-design.md](auth-design.md) 6장).

## 6. 테스트 데이터

`php artisan db:seed`는 관리자 계정(`admin@example.com`)과 고객 앱 테스트 계정(`test@example.com`)을 만들고, 테스트 계정에 가게 4곳과 포인트를 넣어요. 충전 상품은 포인트 묶음의 충전 금액과 맞췄고, 포인트도 충전 상품도 없는 가게(아침베이커리)도 하나 있어요. 비밀번호는 `DatabaseSeeder`와 `UserFactory`에 있어요.
`migrate:fresh`는 개발 DB를 지워요. `--env=testing`을 붙여도 `.env.testing`이 없으면 `.env`의 개발 DB를 써요.

## 7. 아직 정할 것

| 항목 | 선택지 / 메모 |
|---|---|
| 공유 방식 | 넘겨주기(받은 사람 것이 됨) / 빌려주기(보낸 사람 것으로 남고 끄면 못 씀, 시안 07-06 토글) |
| 유효기간 기본값 | 충전포인트 `[N]`일, 서비스포인트 `[N]`일 (시안은 D-365, D-100) |
| 여러 묶음 중 먼저 쓰는 순서 | 기한이 빠른 것부터 / 서비스포인트부터 / 충전포인트부터 |
| 기한이 지난 충전포인트 | [환불 / 소멸 / 기타] |
| 포인트 변동 기록 | 충전·쓰기·환불을 만들 때 묶음별 기록 테이블을 함께 만들어요 |
| 02-01 홈 친구 초대 배너 | "둘 다 5,000P" 이벤트 보상을 남길지. 리뷰·이벤트 적립금을 없앤 것과 맞지 않아요 |
